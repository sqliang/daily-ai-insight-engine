## 1. 设计动机

### 1.1 旧日志系统的四大问题

在实施统一日志之前，pipeline 的日志处于**无统一设计**状态：

1. **配置分散**：`logging.basicConfig()` 在 3 个 stage CLI（extract、analyze、synthesize）中各自调用，且行为不一致 — extract/analyze 的 `--verbose` 设 DEBUG，synthesize 设 INFO
2. **覆盖不全**：Stage 1（scout/ingest/backfill-ids）和 aggregate 完全没有 logging 配置，所有状态输出依赖 `print()` 到 stdout
3. **无持久化**：所有日志仅输出到 stderr，没有文件 handler，一次运行结束后日志即丢失，无法回溯调试
4. **print 与 logging 混用**：~80+ 处 `print()` 调用与 14 个 `logger.info/warning/error` 并存，没有统一的级别控制

### 1.2 设计目标

- **配置集中**：一个 YAML 文件 + 一个初始化函数，所有模块零改动继承
- **终端可读**：运行时在终端看到简洁的 `HH:MM:SS [LEVEL] module: message` 格式
- **文件可查**：每次运行自动写入 `logs/日期/{stage}.log`，含文件名+行号，支持 `grep` 定位源码
- **按日期 + stage 隔离**：不同日期不同目录，不同 stage 不同文件，互不干扰
- **标准库零依赖**：纯 Python 标准库 `logging.config.dictConfig` + `RotatingFileHandler`

## 2. 架构概览

```
                              pipeline/run.py
                              ┌──────────────────────────────┐
                              │ args = parser.parse_args()   │
                              │ init_logging(                 │
                              │   stage=args.command,        │
                              │   verbose=args.verbose,      │
                              │ )                             │
                              │ args.func(args)  ───► 各 stage execute() │
                              └──────────────┬───────────────┘
                                             │
                     ┌───────────────────────┼───────────────────────┐
                     │                       │                       │
                     ▼                       ▼                       ▼
        pipeline/logging_config.yaml    pipeline/core/         各模块 logger
        ┌──────────────────────┐       logging_config.py      ┌──────────────────────┐
        │ formatters:          │       ┌─────────────────┐    │ logger = getLogger() │
        │   brief   (终端)     │──────▶│ 1. 加载 YAML     │    │   (14 个模块, 不改动)  │
        │   detailed (文件)    │       │ 2. 注入 file     │◀───│                      │
        │                      │       │    handler       │    │ pipeline.ingestion.  │
        │ handlers:            │       │ 3. 调整 console  │    │ pipeline.extraction. │
        │   console (stderr)   │       │    level         │    │ pipeline.analysis.   │
        │   file_*  (运行时注入)│       │ 4. dictConfig()  │    │ pipeline.synthesis.  │
        │                      │       └────────┬────────┘    └──────────┬───────────┘
        │ loggers:             │                │                       │
        │   pipeline: DEBUG    │                │ 应用配置               │ 日志输出
        │ root: WARNING        │                ▼                       ▼
        └──────────────────────┘       ┌──────────────────────────────────┐
                                       │          日志路由                  │
                                       │                                  │
                                       │  StreamHandler(stderr)           │
                                       │  ├─ brief format                 │
                                       │  └─ level: INFO / DEBUG(--verbose)│
                                       │                                  │
                                       │  RotatingFileHandler             │
                                       │  ├─ logs/2026-05-25/extract.log  │
                                       │  ├─ detailed format              │
                                       │  ├─ maxBytes: 10 MB              │
                                       │  ├─ backupCount: 5               │
                                       │  └─ level: DEBUG (始终)          │
                                       └──────────────────────────────────┘
```

**数据流方向**：`run.py` 启动 → `init_logging()` 加载 YAML + 注入运行时参数 → `dictConfig` 全局生效 → 各模块 `logger = getLogger(__name__)` 自动获得终端+文件双输出

## 3. 核心组件

### 3.1 `pipeline/logging_config.yaml` — 静态配置模板

```
文件: pipeline/logging_config.yaml
角色: 定义 formatter、handler、logger 的结构模板
加载: 由 init_logging() 通过 yaml.safe_load 读取，dictConfig 应用
```

**formatters**（两个）：

| Formatter | 格式 | 用途 |
|-----------|------|------|
| `brief` | `HH:MM:SS [LEVEL] module.name: message` | 终端输出，紧凑可读 |
| `detailed` | `YYYY-MM-DD HH:MM:SS [LEVEL] module.name [filename:lineno]: message` | 文件输出，方便 grep 定位源码 |

**handlers**（两类）：

| Handler | 类 | 目标 | 级别 | 注入时机 |
|---------|-----|------|------|----------|
| `console` | `StreamHandler` | stderr | 运行时由 `--verbose` 决定 | YAML 预定义 |
| `file_{stage}` | `RotatingFileHandler` | `logs/{date}/{stage}.log` | 始终 DEBUG | `init_logging()` 运行时动态注入 |

**loggers**（两层）：

| Logger | 级别 | propagate | handlers |
|--------|------|-----------|----------|
| `pipeline` | DEBUG | false | `[console, file_{stage}]` |
| `root` | WARNING | — | `[console]` |

`root` logger 保持 WARNING 兜底，避免第三方库（`httpx`、`playwright`、`feedparser` 等）的 INFO/DEBUG 日志污染输出。

### 3.2 `pipeline/core/logging_config.py` — 动态初始化逻辑

```
文件: pipeline/core/logging_config.py
入口: init_logging(stage, verbose, log_dir)
调用方: pipeline/run.py (主入口), 各模块 main() (独立入口)
```

核心函数：

```python
def init_logging(
    stage: str = "pipeline",        # 当前 stage，决定日志文件名
    verbose: bool = False,          # True → console handler 设 DEBUG
    log_dir: Optional[Path] = None, # 日志目录，默认 logs/<YYYY-MM-DD>/
) -> None:
```

**执行步骤**：

1. **确定日志目录**：优先 `AI_ENGINE_LOG_DIR` 环境变量 → 默认 `<project_root>/logs/<YYYY-MM-DD>/`
2. **加载 YAML 模板**：读取 `pipeline/logging_config.yaml` 得到 dict
3. **动态注入 file handler**：根据 `stage` 创建 `RotatingFileHandler`，写入 `config["handlers"]`
4. **调整 console 级别**：`verbose=True` → DEBUG, `verbose=False` → INFO
5. **绑定 file handler 到 pipeline logger**：将 `handler_name` 追加到 `pipeline` logger 的 handlers 列表
6. **dictConfig 应用**：一次性应用到整个 Python logging 体系
7. **日志初始化成功**：`logger.info("日志系统初始化完成 stage=... verbose=... file=...")`

**幂等性**：`dictConfig` 的 `disable_existing_loggers: false` 保证重复调用不会清除已有 logger，而 `RotatingFileHandler` 的 `mode='a'`（默认）保证追加写入而非覆盖。

**STAGE_HANDLER_MAP**：将 CLI 子命令名映射到 handler 名，未匹配的 stage 回退到 `"file_pipeline"`：

```python
STAGE_HANDLER_MAP = {
    "scout": "file_scout", "ingest": "file_ingest",
    "backfill-ids": "file_backfill", "extract": "file_extract",
    "analyze": "file_analyze", "aggregate": "file_aggregate",
    "synthesize": "file_synthesize",
}
```

## 4. 初始化流程

```
run.py 启动
  │
  ├─ 1. sys.path 设置
  ├─ 2. load_dotenv(.env)
  ├─ 3. setup_proxy()          ← proxy 初始化（在 agent 调用之前）
  │
  ├─ 4. 注册子命令              ← 各 stage register_subparser()
  ├─ 5. args = parse_args()    ← 解析 --verbose, command
  │
  ├─ 6. init_logging(           ← ★ 日志初始化（在所有 stage 执行之前）
  │      stage=args.command,
  │      verbose=args.verbose,
  │    )
  │
  └─ 7. args.func(args)        ← 派发到具体 execute 函数
       │
       ├─ extraction/cli.py  → orchestrator.py   → agent.py (SDK 调用)
       ├─ analysis/cli.py    → run_analysis.py   → deep_analysis_agent.py
       ├─ synthesis/cli.py   → run_synthesis.py  → editor_in_chief_agent.py
       ├─ ingestion/scout/cli.py → orchestrator.py
       └─ ingestion/ingest/cli.py → orchestrator.py

各模块的 logger = logging.getLogger(__name__) 自动继承 pipeline logger 配置
```

**时序保证**：日志初始化在第 6 步，先于任何业务逻辑（第 7 步）。所有模块的 `logger` 在首次被调用时已获得完整的 handler 配置。

## 5. 日志目录与文件组织

### 5.1 目录结构

```
logs/
├── 2026-05-25/               ← 日期目录
│   ├── scout.log             ← Stage 1a: URL 清单生成
│   ├── ingest.log            ← Stage 1b: 正文抓取与清洗
│   ├── backfill-ids.log      ← 工具: ID 回填
│   ├── extract.log           ← Stage 2: 元信息与事实提取
│   ├── analyze.log           ← Stage 3: 三维度深度分析
│   ├── aggregate.log         ← Stage 4a: Frontmatter 聚合
│   └── synthesize.log        ← Stage 4b: Editor-in-Chief 合成
├── 2026-05-26/
│   ├── extract.log
│   └── ...
└── ...
```

**设计理由**：

- **按日期分目录**：天然的时间轴，便于定期清理（`rm -rf logs/2026-05-01` 删除一个月前的日志）
- **按 stage 分文件**：匹配实际工作流 — 你通常只 debug 某一个 stage，打开对应文件即可
- **跨 stage 追踪**：`grep -r "article_id_abc" logs/2026-05-25/` 一次命令贯穿全流程

### 5.2 日志内容格式

**终端输出**（brief 格式）：
```
11:01:15 [INFO] pipeline.ingestion.scout.cli: Stage 1 Scout 开始 force=False
11:02:43 [INFO] pipeline.ingestion.scout.cli: Stage 1 Scout 完成 sources=22 articles=79
```

**文件输出**（detailed 格式）：
```
2026-05-25 11:01:15 [INFO] pipeline.ingestion.scout.cli [cli.py:55]: Stage 1 Scout 开始 force=False
2026-05-25 11:02:43 [INFO] pipeline.ingestion.scout.cli [cli.py:60]: Stage 1 Scout 完成 sources=22 articles=79
```

文件输出比终端多了 `[filename:lineno]` 字段，`grep` 到关键日志后可直接跳转到源代码位置。

### 5.3 环境变量

| 变量 | 作用 | 默认值 |
|------|------|--------|
| `AI_ENGINE_LOG_DIR` | 日志根目录 | `<project_root>/logs/<YYYY-MM-DD>/` |

用途：在 CI 环境或容器中指向持久化存储位置。

## 6. 日志级别策略

采用**三层级别控制**，实现终端可调（`--verbose`）、文件全记录（始终 DEBUG）：

```
                    ┌──────────────┐
                    │ pipeline logger│  ← level: DEBUG（允许所有消息通过）
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              ▼                         ▼
     ┌────────────────┐       ┌────────────────────┐
     │ console handler │       │  file handler      │
     │ level: 动态      │       │  level: DEBUG (固定)│
     │ --verbose → DEBUG│       │  始终记录所有日志     │
     │ 默认 → INFO      │       └────────────────────┘
     └────────────────┘
```

| 场景 | `--verbose` | 终端显示 | 文件记录 |
|------|-------------|----------|----------|
| 日常运行 | 不带 | INFO 及以上 | DEBUG 及以上（全部） |
| 调试/开发 | `-v` | DEBUG 及以上（全部） | DEBUG 及以上（全部） |
| CI 环境 | `-v` | DEBUG | DEBUG |

### 6.1 `--verbose` 的统一管理

`--verbose` / `-v` 作为 `run.py` 顶层 flag，不再由各子命令独立定义：

```bash
uv run python pipeline/run.py -v extract    # extract 阶段显示 DEBUG
uv run python pipeline/run.py --verbose analyze  # analyze 阶段显示 DEBUG
uv run python pipeline/run.py scout          # 默认 INFO 级别
```

各 stage 的 CLI 不再注册 `--verbose` 参数，避免冲突。

### 6.2 消息类型与级别约定

| 级别 | 使用场景 | 示例 |
|------|----------|------|
| `DEBUG` | 详细的内部状态（跳过原因、字段回退、JSON 修复细节） | `"旧文件缺少 id，回退生成"`, `"跳过（缺少 id/title）"` |
| `INFO` | 正常操作流程（stage 开始/完成、article 计数、关键里程碑） | `"Stage 1 Scout 开始"`, `"BaseInfo 提取完成"` |
| `WARNING` | 可恢复的异常（重试、校验失败修复、降级处理） | `"Agent 调用失败（第 2/3 次）"`, `"QualitativeAssessment 严格校验失败"` |
| `ERROR` | 不可恢复的错误（文件读写失败、Agent 调用最终失败） | `"读取文件失败"`, `"写入输出文件失败"` |

## 7. 日志轮转与清理

### 7.1 文件轮转

使用 `RotatingFileHandler` 防止单个日志文件无限增长：

| 参数 | 值 | 说明 |
|------|-----|------|
| `maxBytes` | 10 MB | 单个日志文件超过此大小自动切分 |
| `backupCount` | 5 | 每个 stage 最多保留 5 个历史分片 |
| `encoding` | utf-8 | 确保中文日志正常写入 |

分割后的文件命名：`extract.log` → `extract.log.1` → `extract.log.2` → ... → `extract.log.5`

**正常情况下不会触发轮转**：单个 stage 单次运行通常产生 < 100 KB 日志。轮转仅作为安全网，防止异常循环或调试模式下的日志爆炸。

### 7.2 清理策略

- **手动清理旧日期**：`rm -rf logs/2026-04-*` 删除上个月的日志
- **定期自动清理**（建议添加到 crontab）：`find logs/ -maxdepth 1 -type d -mtime +30 -exec rm -rf {} \;`
- **`.gitignore` 已忽略 `logs/`**：不会意外提交

## 8. 使用方式

### 8.1 基本命令

```bash
# 日常运行（终端 INFO，文件 DEBUG）
uv run python pipeline/run.py scout
uv run python pipeline/run.py ingest
uv run python pipeline/run.py extract

# 调试运行（终端 DEBUG，文件 DEBUG）
uv run python pipeline/run.py --verbose extract
uv run python pipeline/run.py -v analyze --stage qualitative

# 指定日志目录（覆盖默认）
AI_ENGINE_LOG_DIR=/var/log/pipeline uv run python pipeline/run.py synthesize
```

### 8.2 日志查询

```bash
# 查看某次 extract 的完整日志
cat logs/2026-05-26/extract.log

# 追踪某篇文章的处理链路
grep -r "0a9e72cc64d162f9" logs/2026-05-26/

# 找出所有 Agent 调用失败记录
grep "Agent 调用失败" logs/2026-05-26/extract.log

# 按级别过滤
grep "\[ERROR\]" logs/2026-05-26/*.log
grep "\[WARNING\]" logs/2026-05-26/*.log

# 统计各 stage 的耗时（通过第一条和最后一条日志的时间戳）
head -1 logs/2026-05-26/extract.log && tail -1 logs/2026-05-26/extract.log
```

### 8.3 在代码中添加日志

现有模块不需任何改动。新模块按照既定模式：

```python
import logging

logger = logging.getLogger(__name__)

def my_function():
    logger.info("处理开始 source=%s count=%d", source_name, count)
    # ...
    logger.warning("重试 %d/%d: %s", attempt, max_attempts, error)
    # ...
    logger.error("处理失败: %s", exc)
```

所有模块使用 `getLogger(__name__)`，自动获得 `pipeline.*` 命名空间下的 handler 配置。消息使用 `%s` / `%d` 占位符（Python logging 的 lazy interpolation 惯例），不在日志调用中使用 f-string。

## 9. print 与 logging 的关系

本方案**不一次性替换全部 `print()`**，而是让两者各司其职：

| 维度 | `print()` | `logging` |
|------|-----------|-----------|
| **目标受众** | 终端用户（实时查看进度） | 开发者（事后回溯分析） |
| **输出目标** | stdout | stderr + 文件 |
| **级别控制** | 无 | INFO/WARNING/ERROR/DEBUG |
| **结构化** | 自由文本 | `[HH:MM:SS] [LEVEL] module [file:line]: msg` |
| **持久化** | 否（除非 shell 重定向） | 是（自动写入文件） |

**迁移策略**：

- **P0（已实施）**：各 stage 的 CLI 入口（`execute()` + `main()`）同时使用 `print()` 和 `logger`，关键状态（开始/完成/article 数）双写
- **P1（后续）**：逐步替换各 stage `orchestrator.py` 中的 `print()` 为 `logger.info()`，保留 `print()` 给用户可见的实时进度
- **P2（后续）**：替换 `pipeline/core/proxy_utils.py` 等工具模块的 `print()`

> **原则**：`print()` 负责用户实时体验，`logging` 负责可审计的持久化记录。两者不互斥，逐步演进。

## 10. 关键设计决策

### 10.1 为什么选择 `dictConfig` 而非继续用 `basicConfig`

- `basicConfig` 只能调用一次（重复调用无效），且不支持多 handler、多 formatter
- `dictConfig` 支持任意复杂的 handler/formatter/logger 配置，且 `disable_existing_loggers: false` 保证幂等
- YAML 配置可读可维护，比代码中的 `basicConfig()` 调用更直观

### 10.2 为什么按日期分目录 + 按 stage 分文件

- **按日期分目录**：自然的时间维度，清理简单（按目录删），轮转自然（一天一个目录）
- **按 stage 分文件**：匹配实际调试模式（你通常只 debug 某一个 stage），文件小便于 `grep`
- **不按 source 拆分**：19 个源 × 7 个 stage = 133 个小文件，心智负担大，且 cross-source 查询困难

### 10.3 为什么 file handler 运行时动态注入

YAML 中 `RotatingFileHandler` 的 `filename` 依赖运行时信息（今日日期 + 当前 stage 名），无法在静态文件中写死。`init_logging()` 用 Python 代码计算路径后注入 `config["handlers"]`，再传给 `dictConfig`。

### 10.4 为什么不引入 `loguru` / `structlog`

- 标准库 `logging` 已满足需求（多 handler、多 formatter、轮转）
- 零额外依赖，不增加 `requirements.txt` 和维护负担
- 14 个现有模块的 `logger = logging.getLogger(__name__)` 无需改动
- 如果未来需要 JSON 格式输出或分布式追踪，标准库也可以升级为 `structlog`（它兼容标准 `logging` handler）

### 10.5 为什么 root logger 设 WARNING

Pipeline 依赖多个第三方库（`httpx`、`playwright`、`feedparser`、`trafilatura`），它们的 INFO/DEBUG 日志对 pipeline 调试无价值。root logger 设 WARNING 兜底，只对 `pipeline` namespace 放开 DEBUG，确保日志不被第三方噪音淹没。
