Flagship Snapdragon provides much better CPU and GPU performance and provide more of what's needed via isolated components on the SoC. That includes better cellular, Wi-Fi/Bluetooth and GNSS radios with solid security including good isolation. Snapdragon Pixels worked well for us and it will again.

Tensor was a sidegrade or downgrade from Snapdragon in many ways. Tensor is paired with the fantastic Titan M2/M3 which was a huge security advantage. It also brought hardware memory tagging (MTE) with the Pixel 8. Snapdragon 8 Elite Gen 5 finally shipped MTE but it's broken on the non-Elite SoC.

Next generation Snapdragon will have more mature support for MTE and greatly improved secure element support. It's still likely going to be a lot of work to get MTE fully deployed for the kernel and OS. We need all our hardware-based features including our USB-C port protection ported to it too.

These devices will meet or exceed of our official requirements including 7 years of proper updates, starting out with the Linux 6.18 LTS which can be upgraded to a new branch eventually, reset attack protection for firmware boot modes and everything else. There wasn't time to do it all for 2026.

It's very realistic to provide better security than Pixels against remote attacks. It's far harder to provide a secure element as good as the Titan M2/M3. There will definitely be a decent secure element providing the current generation features including the Android 16 QPR2+ rate limiting design.

Pixels have become much harder to support. AOSP 16 removed support for Pixels and they became harder to properly support than many other devices rather than easier. It's crucial to keep up with the major OS updates to provide all the security patches and we do but it's much harder for us now.

Motorola is doing a large portion of the work of porting GrapheneOS to their devices. They'll provide us with what we need for firmware/drivers in the form we need it and it will be far easier than Pixels. We'll be able to get issues in the firmware and drivers fixed through Motorola and Qualcomm.

We do plan to support Motorola's Razr Fold and Razr Ultra (flip) devices in addition to a regular device. We already support the original Pixel Fold (Pixel 7) along with the Pixel 9 Pro Fold and Pixel 10 Pro Fold. We still plan to add support for 11th gen Pixels including the Pixel 11 Pro Fold too.

Supporting a flip device with vertical folding would be a new form factor for GrapheneOS. The main use case for those is a tiny phone to use with one hand in the folded form factor. The tablet-style folding devices we already support are extremely useful for web browsing, reading, maps, etc.

@computer @UninterestedNerd @benlovesboba Pixel 9a and earlier were officially the Android Open Source Project (AOSP) reference devices. It included official support for them including the sources for the kernel drivers and a large portion of the userspace device support code. They didn't have things set up for proper production builds with the vendor code built from sources so we had to put that together ourselves.

Android 16 removed support for Pixels from AOSP and we had to develop it again.

@computer @UninterestedNerd @benlovesboba A substantial part of our resources is spent on developing and maintaining support for making production builds of AOSP for Pixels. There's also a large portion of our resources used on making our hardening features work on Pixels. A subset of our features are hardware-based including hardware memory tagging, USB-C port protection and others. Hardware memory tagging also uncovers a massive number of memory corruption bugs in software in practice.

@computer @UninterestedNerd @benlovesboba Google has hardware memory tagging for a tiny set of processes as part of Android Advanced Protection Mode (AAPM) added in Android 16. They don't use it for the kernel, don't use it for the vast majority of AOSP userspace processes and don't use it for the device-related processes in the vendor HAL. They also don't use it for apps not explicitly opting into it which are negligible. We use it for the whole kernel and userspace including all base OS apps.

@computer @UninterestedNerd @benlovesboba We sometimes have to exclude a few processes from hardware memory tagging when there are invalid memory accesses occurring during regular use. For open source code, it's at least feasible for us to figure it out and fix it. We have to do that for anything caught in the kernel in practice, but for userspace processes we decide if it's worth doing based on the importance of the process. It's too hard to fix in Pixel userspace driver HAL processes now.

@computer @UninterestedNerd @benlovesboba It's possible that it will take us months to support the new Pixel 11 devices because of how hard it is to add support for them now. We used to be able to add support for the newly launched devices in under 24 hours from receiving them and the code being pushed which was done on launch day. Prior to Android 16, Pixel 11 devices would have had all of their kernel sources and a large portion of the userspace sources pushed to AOSP in a device branch now.

@computer @UninterestedNerd @benlovesboba Instead, we have to request the kernel driver sources via a Google Forms setup (https://source.android.com/opensourcerequest) and they provide a link to the tarballs for the specific tag we requested. They throw all the code from dozens of Git repositories into a single massive tarball with no commit history. It can't be uploaded to GitHub as a single repository due to size. It also breaks uploading to GitLab even with our free Enterprise so we had to split adding files.

@computer @UninterestedNerd @benlovesboba They no longer provide the setup for building AOSP for Pixels or the userspace driver / service code for them. We use automated tooling we developed in partnership with ProtonAOSP and have continued for years after ProtonAOSP developed stopped. The original purpose of the tooling was adding all the missing configuration and building Pixel userspace driver/service code from source instead of simply using the prebuilt code as they suggested to people.
