- **为什么重要**: 该发现揭示了 AI Agent 生态的一个深层结构性矛盾：Anthropic 的 RL 后训练针对 Claude Code 的宽容客户端进行了适配，导致 Opus 4.8 和 Sonnet 5 在通用严格工具定义场景下编造额外字段（requireUnique、oldText2、matchCase 等十余种），而老版本模型无此问题。OpenAI Codex 凭借 Harmony 格式的受限解码（constrained decoding）机制完全规避了此类回归，形成了架构级护城河。所有基于 Anthropic API 构建 Agent 系统的团队需立即评估工具调用可靠性风险，并关注 strict 模式的使用限制。

**支撑证据**:

- Armin Ronacher 发现 Opus 4.8 和 Sonnet 5 在调用 Pi 的 edit 工具时，在 edits[]数组中编造 requireUnique、oldText2、matchCase 等额外字段键，导致工具调用被拒绝，而老版本模型无此问题。 [1]

## 深度分析

### AI Agent 工具调用的可靠性危机：从 Claude 字段编造到 GPT-5.5 推理截断

**背景**: 7 月 4 日至 5 日，两项独立的 AI Agent 基础设施层问题被曝光：Armin Ronacher（Flask/Jinja2 作者）通过可复现实验发现 Claude Opus 4.8 和 Sonnet 5 在嵌套工具调用中编造额外字段，且问题随模型版本更新而恶化；另一用户通过 39 万条生产日志分析发现 GPT-5.5 Codex 的推理令牌异常集中在 516 固定值，516 截断率从 2 月的 0.11%飙升至 6 月的 35.84%。两项发现均指向一个核心问题：更强的模型未必更可靠地执行工具调用。

**影响**: 这些发现将深刻影响 AI Agent 生态的竞争格局。OpenAI 的 Harmony 格式（受限解码）展示了架构级优势，而 Anthropic 的 RL 优化针对宽容客户端生态的'逆向学习'效应暴露了开放 API 与封闭工具生态之间的根本性矛盾。依赖 Anthropic API 构建 Agent 系统的团队面临两难：使用 strict 模式受限于工具定义复杂度，不使用则面临模型编造字段的风险。GPT-5.5 推理截断问题若被证实为隐性机制，将严重侵蚀用户对付费推理模型的信任，加速企业用户向竞品迁移。

**后续关注**: 需持续关注三大指标：一是 Anthropic 是否发布针对工具调用可靠性的专项修复或官方回应；二是 OpenAI Codex 团队对 GPT-5.5 推理令牌聚类问题的调查结论（#29353 号 issue）；三是受限解码（grammar-constrained decoding）技术栈是否从模型内置能力向 Agent 中间件层扩散，形成新的基础设施赛道。此外，企业级 Agent 部署团队应建立模型版本回归测试流程，针对核心工具 schema 进行多轮 agentic 交互测试。
